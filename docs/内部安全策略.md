# 内部开源依赖安全策略（v1.0）

> 本文件是 DepGuard 内部知识库的示例文档，供「内部知识助手」检索，演示 RAG 能力。
> 覆盖：漏洞分级处置、许可证合规、依赖升级、审批流程、例外规则。

---

## 一、漏洞分级与处置时限（SLA）

| 严重等级 | CVSS 分数 | 定义 | 处置时限 |
|---------|----------|------|---------|
| Critical | 9.0 - 10.0 | 可远程利用、导致 RCE / 数据泄露 | **24 小时内**升级或热修 |
| High | 7.0 - 8.9 | 认证绕过、任意文件读取、严重 DoS | **7 天内**升级 |
| Medium | 4.0 - 6.9 | 需特定条件触发的漏洞 | **30 天内**升级 |
| Low | 0.1 - 3.9 | 影响有限、难以利用 | 随下个版本迭代修复 |

**硬性规定**：
1. Critical 级漏洞必须**当日升级**，无法立即升级时需提交书面豁免并经过安全负责人审批。
2. 已停止维护（EOL）的依赖版本，无论当前是否爆漏洞，一律列入升级清单。
3. 漏洞修复**优先升到官方安全版本**（OSV `fixed` 字段），不推荐跨大版本。

## 二、许可证合规政策

| 许可证 | 使用策略 |
|--------|---------|
| MIT / Apache-2.0 / BSD / ISC | ✅ 允许，直接使用 |
| LGPL / MPL / EPL | ⚠️ 允许，但需合规评审（注意链接方式） |
| GPL / AGPL | ❌ **禁止**，商用产品不得引入 |
| 无许可证 / 未知 | ❌ 禁止，需法务确认 |

**规定**：引入任何新依赖前，必须通过 `deps.dev` 或 `osv-scanner --licenses` 确认许可证类型。

## 三、依赖升级策略（保守优先）

1. 默认采用**保守升级**：只升到「修复该漏洞的最小安全版本」，不跳大版本。
2. 遇到破坏性变更（breaking changes）时，需：
   - 评估影响范围；
   - 在测试分支跑完整 CI；
   - 通过后再合并主分支。
3. 大版本升级（如 requests 2.x → 3.x）必须走单独的技术评审。

## 四、白名单与已知例外

### 白名单（允许继续使用的低风险旧版本）
- `pytz 2022.1`：仅时区数据包，无已知可利用漏洞，允许沿用至下一季度。
- `python-dateutil 2.8.2`：无已知高危漏洞，随常规升级窗口处理。

### 已知忽略的 CVE（误报 / 不可利用）
- `CVE-2020-XXXX`（示例）：该漏洞需本地已认证用户触发，我司部署环境不适用，标记为「忽略」。
- 忽略决策需在 `scan_trace` 中记录证据链，每季度复核一次。

## 五、升级审批流程

1. 漏洞扫描报告（含 severity / CVE / 修复版本）由自动化流程生成。
2. Critical / High 漏洞：安全负责人审批后，开发 24h/7d 内执行升级。
3. 升级 PR 必须包含：漏洞编号、修复版本、CI 通过截图、回滚方案。
4. 生产环境升级需灰度发布，观察 24 小时无异常后全量。

## 六、持续监控要求

- 依赖清单纳入 CI 流水线，每次提交自动触发漏洞扫描。
- SBOM（CycloneDX 格式）随每次发布版本化归档。
- 每季度进行一次全量依赖复查，更新白名单与忽略清单。
